# 記事の問題報告フォーム

各記事の「この記事の問題を報告」は、Googleフォームを開かずにサイト内で送信できるフォームです。公開Worker `atlasez01` の `POST /api/article-reports` が内容を受け取り、本番では公開サイト・運営サイトが共有するD1の `article_reports` テーブルへ保存します。

## Discord通知（任意）

保存成功後、公開Workerは記事名・記事URL・分野・カテゴリ・報告種別だけをDiscordへ通知します。報告本文・返信先・hashはDiscordへ送りません。設定された場合は共有Secret付きでADMIN内部APIにも中継します。中継に失敗しても公開側D1への保存は失敗しません。

公開Workerの `wrangler.jsonc` は `ARTICLE_REPORT_INGEST_URL` に `https://atlasez-admin.ukyoukay0.workers.dev/internal/article-reports` を宣言しています（2026-10-12時点）。Cloudflareへ登録された実効値・到達性は未確認です。`ARTICLE_REPORT_INGEST_TOKEN` が設定されると、公開Workerは報告内容を共有Secret付きで運営Workerの内部APIにも送ります。トークン値はGitHubやチャットへ保存・投稿しません。本番の公開Workerと運営Workerは同じD1を参照するため、DB保存後のこの中継は必須の保存経路ではありません。実際に使う理由、接続先、運営画面に対する効果を運営担当が確認するまで、接続先の変更・中継の有効化をしないでください。

Discord通知は内部API中継とは独立しています。Webhook URLはSecretとして保管し、GitHubやチャットへ保存しません。チャンネル準備やDiscordロール設定の実運用手順はADMIN側の運用文書に従ってください。

### 公開前の依存条件

この文書と公開プライバシーポリシーに記載する7日・30日・180日の削除処理はADMIN側の変更です。ADMIN変更を正規経路でmainへ反映し、固定Workerで毎時Cronの成功と隔離データの削除結果を確認してから公開サイトを更新してください。記事報告用 `REPORT_IP_HASH_SALT` を登録し、値を表示せずSecret名だけを確認することも必要です。ADMIN Workers Builds復旧、Secret登録、保持処理の配信/確認のどれかが未完了なら、公開サイトの同時リリースは停止します。

## 運営用の確認画面

`https://admin.atlasez.org/admin/reports/` で、届いた報告の一覧、対応状況（未確認・確認中・対応済み）、現在の運営メモを管理できます。Google OAuthで認証し、担当分野の権限を持つ運営担当者と全体管理者だけが本文・返信先を閲覧できます。変更前の状態を並べる履歴画面はありません。運営サイトの利用者向け本番URLは `https://admin.atlasez.org` です。

## ローカルで確認する

初回だけ、別のターミナルでローカルD1にテーブルを作ります。

```bash
npm run db:reports:local
```

次に静的サイトをビルドし、Worker 経由で開きます。

```bash
npm run build
npm run dev:reports
```

`http://localhost:8787/atlas/ja/.../` の記事下部で送信を確認できます。ローカル保存済みの報告は次のコマンドで閲覧できます。

```bash
npx --yes wrangler d1 execute atlasez-reports-local --local --config wrangler.local.jsonc --command "SELECT article_title, report_type, details, created_at FROM article_reports ORDER BY created_at DESC"
```

## 送信データと対策

- 自動添付: 記事名、記事URL、記事ID、分野、カテゴリ、表示言語
- 利用者入力: 報告種別、内容、返信先（任意）
- 迷惑送信対策: 非表示のハニーポット、入力長の制限、送信前の最小滞在時間、同一記事・同一内容の7日間の重複拒否
- 連投対策: 送信回数制限のため、アクセス元IPとWorker Secret `REPORT_IP_HASH_SALT` を使ったハッシュを保存し、1時間あたり3件・24時間あたり8件までに制限。生のIPアドレスはD1へ保存しない。ソルトが未設定の場合は弱いハッシュを保存せず、送信を受け付けない
- 重複対策: 記事ID・報告種別・本文から作成する重複判定用ハッシュは、報告作成後7日を超えるとADMINの毎時処理で消去する
- 保持期限: 報告者ハッシュは報告作成から30日後、対応済み報告の返信先は最終更新から180日後にADMINの毎時実行される個人情報削除処理で消去する。未解決報告の返信先に自動削除期限はなく、対応済みになるまでの上限は運営決定待ち
- 報告本文・現在の運営メモには固定の自動削除期限を設定していない。変更前の状態を記録する対応履歴は保存していない。保持期間・不要になった記録の削除手順は運営決定事項であり、応募募集の一般公開前に確定する
- 上記の削除処理は稼働中D1の値を対象とする。Time Travel snapshotや取得済みexport内のコピーを自動削除するものではない。バックアップコピーのアクセス制限、保持期間、削除方法は別途決定する。

## 閲覧統計（運営サイト）

`/admin/reports/` の「閲覧統計」タブで、公開記事の閲覧・読了状況を見られる。

| 列       | 意味                                         |
| -------- | -------------------------------------------- |
| 閲覧     | ページを開いた回数                           |
| 読まれた | 一定量スクロールされた回数                   |
| 90%到達  | 記事末尾まで到達した回数                     |
| 完読率   | 90%到達 ÷ 閲覧。低いほど途中で離脱されている |
| 報告     | 同じ期間にその記事へ寄せられた問題報告の件数 |

並べ替えは2種類ある。

- **よく読まれた順**: 90%到達の多い順。何が読まれているかを見るとき
- **直す価値が高い順**: 閲覧が5件以上ある記事のうち完読率が低い順。**どれを直すか決めるとき**

完読率が30%を下回る記事には「要改善」を添える。読まれているのに最後まで届いていない記事は、
説明の順序・前提の不足・分量のどれかに原因があることが多い。
