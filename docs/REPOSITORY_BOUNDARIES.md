# リポジトリとデータの境界

現在は、公式サイト・学習サイトを`Atlasez01`で、認証付き運営サイトを
[`Admin-Atlesez`](https://github.com/Atlasez/Admin-Atlesez)で管理する。過去のモノレポ時代の
文書・履歴には運営コードの記述が残るが、現在の実装とSecret・D1の正本は分離されている。
次の境界を維持する。

## 1. サイト／管理画面コード

`Atlasez01`では`src/pages/`、`src/layouts/`、`src/components/`、`src/lib/`、`src/styles/`、`scripts/`が対象。ここには個人情報、D1の本番データ、APIキーをコミットしない。表示設定、言語切替、パンくずなど公開側の横断UIは共通コンポーネントへ置く。認証、ToDo、日程、通知などの運営UIは`Admin-Atlesez`側に置く。

## 2. 記事本文・翻訳・分類

記事は `src/content/articles/<ISO 639-3>/`、概念は `src/content/concepts/`、分野は `src/content/subjects/` に置く。日本語は `jpn`、英語は `eng` のように3文字コードを保存単位にする。公開URLで使っている `ja`／`en` は利用者向けの互換エイリアスであり、保存場所の命名規則とは分ける。

## 3. 画像・動画などの大容量ファイル

小さい公開アセットはGitで管理できるが、画像・動画が増えたらCloudflare R2などのオブジェクトストレージへ移す。GitにはアセットID、サイズ、代替テキストなどのメタデータだけを残し、本文は安定したアセットIDを参照する。これによりGit履歴の肥大化と記事データの分割を避けられる。

## 4. コメント・履歴・ToDoなどの運用データ

個人情報を含む運用データは`Admin-Atlesez`側のD1に置き、記事リポジトリとは分離する。ToDoはプロジェクトIDを必須にした共通データとして扱い、学習サイト・ゼミプラットフォーム・運営事務局で同じ項目（担当者、期限、状態、リマインダー）と状態値を使う。各プロジェクトのAPIはこの共通データを絞り込んで返し、メンバー用Homeでは参加中プロジェクトの未完了ToDoを横断表示する。

共通ToDoへの統合は`Admin-Atlesez`側のmigrationで行う。既存の`editorial_tasks`を正規テーブルとして`project_id`を追加し、旧`atlasez_project_todos`の行を一度だけ取り込む。旧表はロールバック確認用に残すが、新規作成・更新は正規テーブルだけに書き込む。管理用migrationを`Atlasez01`へコピーしない。

この境界を守れば、将来「コード」「記事・翻訳」「大容量アセット」「運用DB」を別リポジトリ／別サービスへ移しても、公開URL・記事ID・プロジェクトIDを維持したまま段階的に移行できる。
